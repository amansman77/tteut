# ADR-PROD-008 단어 페이지를 의미망(Semantic Network) 구조로 확장

## 상태

승인

## 맥락

현재 뜨읏은 `/word/[slug]` 기반 공개 페이지를 중심으로 성장하고 있다.

현재 구조는 다음과 같다.

```
단어
→ 사전적 의미
→ 살아낸 뜻들
→ 사용자 입력
```

이 구조는 초기 SEO 및 의미 기록 구조로는 충분히 유효하다.

그러나 시간이 지나며 다음과 같은 문제가 생기기 시작했다.

1. 단어가 서로 연결되지 않는다
2. 검색 이후 탐색 흐름이 약하다
3. 플랫폼이 "의미 생태계"보다 "독립 페이지 목록"처럼 보인다
4. 살아낸 뜻 사이의 관계가 드러나지 않는다
5. 언어가 축적되지만 관계가 축적되지 않는다

예를 들어:

* 공감 ↔ 경청
* 관계 ↔ 연결
* 균형 ↔ 중심

과 같은 의미적 연결이 실제 데이터 안에 존재하지만,
현재 시스템은 이를 구조적으로 표현하지 못한다.

뜨읏은 단순 사전(Dictionary)이 아니라:

> 사람이 살아낸 언어들이 서로 연결되며 의미를 만들어가는 플랫폼

을 지향한다.

따라서 단어(node)뿐 아니라 의미 관계(edge)를 함께 다루는 구조가 필요해졌다.

## 결정

뜨읏은 기존 단어 페이지 구조를 유지하면서,
단어 간 의미 관계를 저장하는 Semantic Network 구조를 추가한다.

현재 단계에서는 Vector DB, pgvector, 실시간 embedding retrieval은 도입하지 않는다.

현재 인프라는 Cloudflare D1 기반으로 유지하며,
의미 관계는 배치(batch) 기반으로 생성하여 저장한다.

### Semantic Edge 구조

```
semantic_edges
- from_word  (TEXT)
- to_word    (TEXT)
- score      (REAL)
- reason     (TEXT)
- generated_at (TEXT)
```

### Edge 생성 방식

1. 뜻 간 공통 키워드 overlap (한국어 토큰 추출 후 교집합)
2. 부분 문자열 매칭 (어근 공유)
3. 운영자 보정

Edge는 실시간 계산하지 않고, 어드민 API(`POST /api/admin/semantic-edges/generate`) 기반 배치 작업으로 생성한다.

### UI 표현 방식

```
이 뜻과 닿아있는 말

경청
관계
연결
```

## 근거

### 현재 단계에서 Vector Infrastructure는 과하다

현재 뜨읏 규모(단어 수십~수백)에서 Vector DB, ANN search, 실시간 semantic retrieval은
운영 복잡도 대비 효과가 낮다.

### Cloudflare D1 구조와 잘 맞는다

Semantic edge를 materialized cache 형태로 저장하면:

* 실시간 연산 부담 감소
* SEO 페이지 연결 강화 (내부 링크 증가)
* 운영 단순화

### 실시간 계산보다 "축적된 관계"가 뜨읏 철학과 맞다

뜨읏은 실시간 AI 검색 엔진보다 삶의 의미가 축적되는 공간에 가깝다.
nightly batch, edge cache, 점진적 관계 형성 방식이 오히려 뜨읏의 감성과 더 잘 맞는다.

## 포기한 대안

- **Vector DB 도입**: 현재 규모 대비 과한 구조, 운영 복잡도 증가
- **pgvector 도입**: 현재 인프라(Cloudflare D1)와 호환 불가
- **실시간 similarity 계산**: D1 구조와 맞지 않음, 캐시 구조가 더 단순하고 안정적
- **수동 연결만 사용**: 유지 비용 증가, 의미 확장 속도 제한

## 결과

검증할 것:

1. semantic edge 클릭률
2. 단어 간 탐색 깊이
3. `/word/*` 페이지 체류 시간 변화
4. 내부 탐색 기반 재방문 증가 여부
5. semantic edge 생성 품질
6. 어떤 관계 유형이 가장 많이 연결되는가

배울 것:

* 사람들은 어떤 의미 연결에 공감하는가
* 삶의 언어는 어떤 방식으로 군집화되는가
* 뜨읏만의 ontology가 실제로 형성되는가
